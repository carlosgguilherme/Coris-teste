\begin{singlespace}
Este relatório descreve o desenvolvimento de uma aplicação web para a gestão de apólices de
seguro viagem da Mariano Seguros, uma seguradora fictícia, construída como resposta a um desafio
técnico. A aplicação permite cadastrar,
consultar, editar e excluir apólices, calculando o valor do seguro (prêmio) a partir do plano, do
destino, da duração da viagem e da idade do segurado. Além do cadastro, foi construída uma
\emph{dashboard} com indicadores voltados a três públicos: a diretoria, o time de marketing, que
avalia a conversão e o retorno das campanhas, e o time comercial, que acompanha as vendas. A
solução utiliza Laravel no \emph{backend}, React no \emph{frontend} e MySQL como banco de dados
relacional, com desenho de implantação na nuvem Microsoft Azure. O código foi organizado em
camadas, seguindo os princípios SOLID e as práticas de Clean Code, e conta com testes
automatizados. Como resultado, obteve-se um sistema funcional, executável com um único comando
por meio de Docker, cujos indicadores respondem a perguntas reais de negócio.

\vspace{1em}
\noindent\textbf{Palavras-chave:} seguro viagem; aplicação web; Laravel; React; dashboard; SOLID.
\end{singlespace}

\section{Introdução}

O seguro viagem é contratado por quem vai viajar para cobrir despesas médicas, extravio de
bagagem, cancelamento da viagem e outros imprevistos. Para a seguradora, cada contrato é uma
\emph{apólice}: um documento que registra quem é o segurado, para onde vai, por quanto tempo,
qual plano contratou e quanto pagou por isso. O valor pago é chamado de \emph{prêmio}.

Como cenário do projeto, foi adotada a \textbf{Mariano Seguros}, uma seguradora fictícia que vende
seguro viagem por site, agências de viagem, corretores, parceiros e aplicativo.

O desafio proposto consistiu em desenvolver uma aplicação capaz de realizar o ciclo completo de
cadastro dessas apólices (leitura, cadastro, edição e exclusão), aplicando boas práticas de
desenvolvimento e prevendo a implantação na nuvem Microsoft Azure. Como diferencial, buscou-se
ir além do cadastro e transformar os dados das apólices em informação útil para a tomada de
decisão dos times de marketing e comercial, por meio de uma \emph{dashboard} de indicadores.

\subsection{Objetivos}

O objetivo geral foi construir uma aplicação web para a gestão de apólices de seguro viagem,
com cálculo automático do prêmio e indicadores de negócio. Os objetivos específicos foram:

\begin{itemize}
  \item oferecer o cadastro completo de apólices, com validação dos dados e cálculo do prêmio
        em tempo real;
  \item modelar um banco de dados relacional que represente segurados, apólices e as
        informações de vendas, marketing, sinistros e atendimento;
  \item organizar o código em camadas, aplicando os princípios SOLID e as práticas de Clean Code;
  \item criar uma \emph{dashboard} com visões específicas para cada time;
  \item garantir o funcionamento por meio de testes automatizados;
  \item projetar a implantação da solução com componentes da Microsoft Azure.
\end{itemize}

\subsection{Organização do relatório}

A Seção~\ref{sec:requisitos} apresenta os requisitos e a Seção~\ref{sec:tecnologias}, as
tecnologias escolhidas. A arquitetura é descrita na Seção~\ref{sec:arquitetura} e o modelo de
dados, na Seção~\ref{sec:dados}. As regras de negócio estão na Seção~\ref{sec:regras} e a

e a Seção~\ref{sec:execucao}, da execução e da implantação. Por fim, a
Seção~\ref{sec:conclusao} traz as considerações finais.

\section{Requisitos}\label{sec:requisitos}

Os requisitos foram definidos a partir do enunciado do desafio e divididos entre funcionais,
que descrevem o que o sistema faz, e não funcionais, que descrevem como ele deve ser construído.

\subsection{Requisitos funcionais}

\begin{itemize}
  \item \textbf{RF01} -- Listar as apólices, com busca por nome, CPF, e-mail ou número da
        apólice, filtro por situação e paginação.
  \item \textbf{RF02} -- Cadastrar uma apólice, informando os dados do segurado, o destino, o
        plano e o período da viagem.
  \item \textbf{RF03} -- Calcular o prêmio automaticamente, exibindo o valor enquanto o
        formulário é preenchido.
  \item \textbf{RF04} -- Editar uma apólice, recalculando o prêmio, e cancelá-la ou reativá-la.
  \item \textbf{RF05} -- Excluir uma apólice, mantendo o registro para fins de auditoria.
  \item \textbf{RF06} -- Exibir indicadores de vendas, marketing, sinistros e atendimento,
        filtrados por período.
\end{itemize}

\subsection{Requisitos não funcionais}

\begin{itemize}
  \item \textbf{RNF01} -- \emph{Frontend} em React, versão 17 ou superior.
  \item \textbf{RNF02} -- \emph{Backend} em PHP, conforme autorização da equipe de tecnologia da
        empresa para este candidato.
  \item \textbf{RNF03} -- Banco de dados relacional.
  \item \textbf{RNF04} -- Código seguindo os princípios SOLID e as práticas de Clean Code.
  \item \textbf{RNF05} -- Desenho da solução com componentes da Microsoft Azure.
  \item \textbf{RNF06} -- Interface em português, com valores em reais e datas no formato
        dia/mês/ano.
\end{itemize}

\section{Arquitetura da solução}\label{sec:arquitetura}

\subsection{Visão geral}

A aplicação é dividida em duas partes independentes que se comunicam por HTTP, trocando dados
no formato JSON. O \emph{backend} é uma API REST responsável pelas regras de negócio e pelo
acesso ao banco de dados. O \emph{frontend} é uma aplicação React que apenas exibe as
informações e envia os formulários, sem conter regras de negócio. Essa separação permite que
cada parte evolua e seja publicada de forma independente.

\subsection{Organização do backend}

O \emph{backend} foi organizado em camadas, e cada camada tem uma única responsabilidade. Quando
uma requisição chega, ela percorre o seguinte caminho:

\begin{enumerate}
  \item a \textbf{rota} (\arq{routes/api.php}) identifica qual ação deve ser executada;
  \item o \textbf{Form Request} (\arq{app/Http/Requests}) valida os dados recebidos; se houver
        erro, a resposta é devolvida imediatamente com a mensagem de cada campo;
  \item o \textbf{Controller} (\arq{app/Http/Controllers/Api}) recebe os dados validados e chama
        o serviço correspondente;
  \item o \textbf{Service} (\arq{app/Services}) aplica as regras de negócio, usando a
        \textbf{Calculadora} de prêmio e os \textbf{Models}, que representam as tabelas;
  \item o \textbf{Resource} (\arq{app/Http/Resources}) converte o resultado para o formato JSON
        esperado pelo \emph{frontend}.
\end{enumerate}

Por exemplo, ao emitir uma apólice, o formulário envia os dados para a rota
\texttt{POST /api/apolices}. O \arq{SalvarApoliceRequest} valida o CPF, as datas e os demais
campos; o \arq{ApoliceController} repassa os dados ao \arq{ApoliceService}, que, dentro de uma
transação, localiza ou cria o segurado pelo CPF, calcula o prêmio, gera o número da apólice e
grava o registro. A resposta volta com o código HTTP 201 (criado).

\subsection{Organização do frontend}

No \emph{frontend}, cada tela fica em \arq{src/pages}, os componentes reutilizáveis em
\arq{src/components} e toda a comunicação com a API em \arq{src/api}. Nenhuma tela chama a API
diretamente: todas usam as funções desse módulo, que padronizam o envio dos dados e o tratamento
de erros. A formatação de moeda, datas e CPF fica concentrada em \arq{src/utils/format.js}.

As Figuras~\ref{fig:lista} e \ref{fig:cadastro} mostram as telas de listagem e de cadastro. No
cadastro, o prêmio aparece à direita e é recalculado enquanto os campos são preenchidos.

Três decisões de modelagem merecem destaque. A primeira é que todos os valores em dinheiro são
armazenados como números inteiros de centavos: o prêmio de R\$~323,70 é gravado como 32370. Os
números de ponto flutuante não representam valores decimais com exatidão, o que poderia gerar
diferenças de centavos, inaceitáveis em valores financeiros. A segunda é que o segurado fica em
uma tabela separada da apólice, identificado pelo CPF, de modo que a mesma pessoa pode ter várias
apólices sem que seus dados sejam repetidos. A terceira é a \emph{exclusão lógica}: ao excluir
uma apólice, o registro não é apagado, apenas recebe a data de exclusão, deixando de aparecer no
sistema, mas permanecendo disponível para auditoria, como exige a atividade de seguros.

As tabelas são criadas por \emph{migrations}, arquivos que descrevem a estrutura do banco e
permitem recriá-lo em qualquer ambiente. As tabelas da \emph{dashboard} foram adicionadas em
\emph{migrations} novas, sem alterar as existentes.

\section{Regras de negócio}\label{sec:regras}

\subsection{Cálculo do prêmio}

O prêmio é calculado pela multiplicação de quatro fatores:

\begin{equation*}
  \text{prêmio} = \text{diária do plano} \times \text{dias de viagem}
  \times \text{fator do destino} \times \text{fator da idade}
\end{equation*}

Os dias contam o primeiro e o último dia da viagem, e a idade é calculada na data de início da
viagem. Os valores de cada fator estão na Tabela~\ref{tab:fatores}.

\begin{table}[H]
\centering
\caption{Fatores do cálculo do prêmio}\label{tab:fatores}
\begin{tabular}{@{}lr@{}}
\toprule
Plano & Diária \\
\midrule
Essencial & R\$ 12,90 \\
Plus & R\$ 24,90 \\
Premium & R\$ 39,90 \\
\bottomrule
\end{tabular}
\qquad
\begin{tabular}{@{}lr@{}}
\toprule
Destino & Fator \\
\midrule
Nacional & 50\% \\
América do Sul & 100\% \\
Europa & 130\% \\
América do Norte & 140\% \\
Ásia, África, Oceania & 150\% \\
\bottomrule
\end{tabular}
\qquad
\begin{tabular}{@{}lr@{}}
\toprule
Idade & Fator \\
\midrule
até 59 anos & 100\% \\
60 a 74 anos & 160\% \\
75 anos ou mais & 250\% \\
\bottomrule
\end{tabular}
\fonte{elaborado pelo autor (2026).}
\end{table}

Como exemplo, uma viagem de 10 dias para a Europa no plano Plus, feita por um segurado de 31
anos, resulta em $2.490 \times 10 \times 1{,}30 \times 1{,}00 = 32.370$ centavos, ou seja,
R\$~323,70. O arredondamento é feito sempre com números inteiros, para o centavo mais próximo.

\subsection{Validações}

Antes de gravar uma apólice, o sistema verifica que todos os campos foram preenchidos, que o CPF
possui dígitos verificadores válidos, que o fim da viagem não é anterior ao início e que a
vigência não passa de 365 dias. No cadastro, o início da viagem não pode ser anterior à data
atual; na edição, essa regra só é aplicada se a data de início for alterada, para que uma
apólice já em vigor continue editável. Uma apólice cancelada só pode ser alterada para voltar a
ficar ativa. Quando alguma regra não é atendida, a API responde com o código HTTP 422 e uma
mensagem em português para cada campo, exibida abaixo do campo correspondente no formulário.

\section{Aplicação dos princípios SOLID e Clean Code}\label{sec:solid}

SOLID é um conjunto de cinco princípios de projeto orientado a objetos que tornam o código mais
fácil de entender, testar e modificar (MARTIN, 2019). Clean Code reúne práticas para que o
código seja legível por outras pessoas (MARTIN, 2009). A Tabela~\ref{tab:solid} aponta onde
cada princípio SOLID foi aplicado.

\begin{table}[H]
\centering
\caption{Onde os princípios SOLID foram aplicados}\label{tab:solid}
\small
\begin{tabularx}{\textwidth}{@{}p{3.3cm}X@{}}
\toprule
Princípio & Aplicação no projeto \\
\midrule
Responsabilidade única (S) & Cada etapa do cadastro é uma classe diferente:
  \arq{SalvarApoliceRequest} valida, \arq{ApoliceController} trata a requisição,
  \arq{ApoliceService} aplica a regra de negócio, \arq{CalculadoraPremioViagem} calcula e
  \arq{ApoliceResource} formata a resposta. Na \emph{dashboard}, o mesmo ocorre com
  \arq{DashboardController}, \arq{DashboardService}, \arq{Metricas} e \arq{Periodo}. \\
\addlinespace
Aberto/fechado (O) & Uma nova regra de preço é criada como uma nova classe que implementa a
  interface \arq{CalculadoraPremio}, sem alterar o serviço. Um novo plano ou destino é uma nova
  opção no enum correspondente, e o \emph{frontend} o exibe sem alteração. \\
\addlinespace
Substituição de Liskov (L) & Qualquer classe que implemente \arq{CalculadoraPremio} pode
  substituir a atual, pois o serviço conhece apenas o contrato da interface. \\
\addlinespace
Segregação de interfaces (I) & A interface \arq{CalculadoraPremio} possui um único método,
  \texttt{calcular}. \\
\addlinespace
Inversão de dependência (D) & O \arq{ApoliceService} recebe a interface no construtor, e não a
  classe concreta; a escolha da implementação é feita no \arq{AppServiceProvider}. \\
\bottomrule
\end{tabularx}
\fonte{elaborado pelo autor (2026).}
\end{table}

O trecho abaixo mostra a inversão de dependência. O serviço depende apenas da interface, e o
\emph{service provider} do Laravel informa qual implementação deve ser usada. Para trocar a regra
de preço, basta alterar essa única linha.

\begin{lstlisting}[language=PHP]
// app/Services/ApoliceService.php
public function __construct(private readonly CalculadoraPremio $calculadora) {}

// app/Providers/AppServiceProvider.php
$this->app->bind(CalculadoraPremio::class, CalculadoraPremioViagem::class);
\end{lstlisting}

Quanto ao Clean Code, as classes e os métodos usam o vocabulário do negócio, como
\texttt{ApoliceService::criar} e \texttt{Metricas::sinistralidade}. Os métodos são curtos e têm
uma tarefa cada: a criação da apólice, por exemplo, delega a outros métodos o registro do
segurado, o cálculo do prêmio e a geração do número. Não há números soltos no código: preços e
fatores ficam nos enums \arq{Plano} e \arq{Destino}, e limites em constantes como
\texttt{VIGENCIA\_MAXIMA\_DIAS}. As fórmulas da \emph{dashboard} estão todas em uma única classe,
\arq{Metricas}, de modo que todas as telas usam a mesma conta. Os erros da API são tratados em um
único lugar, \arq{bootstrap/app.php}, e os nomes dos testes descrevem a regra verificada, como
\texttt{test\_apolice\_cancelada\_so\_pode\_ser\_reativada}.

\section{Dashboard de indicadores}\label{sec:dashboard}

A \emph{dashboard} foi o principal diferencial do projeto. Enquanto o cadastro atende à operação
do dia a dia, a \emph{dashboard} transforma os dados em informação para a tomada de decisão. Ela
foi dividida em quatro visões, cada uma pensada para as perguntas de um time, e todas podem ser
filtradas pelos últimos 30 ou 90 dias ou pelos últimos 12 ou 24 meses.

\subsection{Visão geral}

A visão geral é voltada à diretoria. Ela mostra seis indicadores (prêmio emitido, apólices,
ticket médio, conversão, sinistralidade e NPS), cada um comparado com o período anterior de mesmo
tamanho, e um gráfico do prêmio mês a mês comparado com o mesmo mês do ano anterior
(Figura~\ref{fig:visao-geral}). O gráfico pode exibir 6 ou 12 meses, em linha ou em colunas.

\begin{figure}[H]
  \centering

\subsection{Fórmulas dos indicadores}

Todas as fórmulas estão centralizadas na classe \arq{Metricas}, apresentadas na
Tabela~\ref{tab:formulas}.

\begin{table}[H]
\centering
\caption{Fórmulas dos indicadores}\label{tab:formulas}
\small
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
Indicador & Fórmula \\
\midrule
Ticket médio & prêmio emitido $\div$ número de apólices \\
Conversão & cotações convertidas $\div$ total de cotações \\
ROI da campanha & (prêmio gerado $-$ investimento) $\div$ investimento \\
Custo por apólice & investimento $\div$ apólices vendidas pela campanha \\
Prêmio ganho & prêmio $\times$ (dias de viagem dentro do período $\div$ dias da viagem) \\
Sinistralidade & custo dos sinistros $\div$ prêmio ganho \\
Frequência & sinistros avisados $\div$ apólices emitidas \\
Taxa de negativa & sinistros negados $\div$ sinistros finalizados \\
NPS & \% de notas 9 e 10 $-$ \% de notas de 0 a 6 \\
\bottomrule
\end{tabularx}
\fonte{elaborado pelo autor (2026).}
\end{table}

A sinistralidade usa o prêmio \emph{ganho}, e não o prêmio emitido. Uma apólice vendida hoje
para uma viagem daqui a dois meses ainda não correu nenhum risco; se todo o seu prêmio fosse
considerado de imediato, a sinistralidade de períodos curtos ficaria distorcida.

\subsection{Dados de demonstração}

Para que a \emph{dashboard} pudesse ser avaliada, foi criado um gerador de dados de demonstração
que produz 24 meses de histórico: cerca de 2.800 apólices, 12.800 cotações, 180 sinistros e 1.800
atendimentos. Os dados seguem padrões realistas, como vendas maiores em julho, dezembro e
janeiro, crescimento de 12\% ao ano, campanhas sazonais e conversão menor no celular. O gerador
usa uma semente fixa, de modo que produz sempre os mesmos dados, e pode ser executado mais de uma
vez sem duplicar informações.

\section{Testes}\label{sec:testes}

O projeto possui 40 testes automatizados, escritos com PHPUnit e executados com o comando
\texttt{php artisan test}. Eles se dividem em dois grupos:

\begin{itemize}
  \item \textbf{testes unitários}, que verificam partes isoladas do código: o cálculo do prêmio
        em diferentes combinações de plano, destino e idade; a validação do CPF; e as fórmulas
        dos indicadores;
  \item \textbf{testes de API}, que fazem requisições reais à aplicação e verificam o
        cadastro, a busca, a paginação, a edição com recálculo do prêmio, a regra da apólice
        cancelada, a exclusão lógica, as mensagens de validação e os números de cada visão da
        \emph{dashboard}.
\end{itemize}

Nos testes de API, a data atual é fixada e o banco de dados é recriado a cada teste, para que os
resultados não dependam do dia em que são executados nem da ordem de execução.

\section{Execução e implantação}\label{sec:execucao}

\subsection{Execução local}

Com o Docker instalado, a aplicação completa é iniciada com dois comandos:

\begin{lstlisting}
docker compose up -d --build
docker compose exec api php artisan db:seed
\end{lstlisting}

O primeiro sobe o banco de dados, a API e o \emph{frontend}, e cria as tabelas; o segundo
carrega os dados de demonstração. A aplicação fica disponível em \texttt{http://localhost:3000}.

\subsection{Implantação na Microsoft Azure}

A Figura~\ref{fig:azure} apresenta o desenho da solução na Azure. O \emph{frontend} React é
publicado no \textbf{Azure Static Web Apps}, que o distribui por uma rede de entrega de conteúdo
com HTTPS. A API Laravel é executada no \textbf{Azure App Service}, que permite escalar a
aplicação conforme a demanda. Os dados ficam no \textbf{Azure Database for MySQL}, um banco
gerenciado com cópias de segurança automáticas. As senhas e chaves ficam no \textbf{Azure Key
Vault}, lidas pela API por meio de uma identidade gerenciada, de modo que nenhum segredo fica no
código. A publicação é feita pelo GitHub Actions a cada atualização do repositório.

\section{Considerações finais}\label{sec:conclusao}

O projeto atingiu o objetivo de construir uma aplicação de gestão de apólices de seguro viagem
com o ciclo completo de cadastro, cálculo automático do prêmio e regras reais do negócio de
seguros, como a exclusão lógica para auditoria e o armazenamento dos valores em centavos. O
código foi organizado em camadas, com a aplicação dos princípios SOLID e das práticas de Clean
Code identificada em pontos concretos, e o funcionamento é garantido por testes automatizados.

Como diferencial, a \emph{dashboard} oferece a cada time as informações de que ele precisa: o
marketing avalia a conversão e o retorno das campanhas, o comercial acompanha as vendas em
valores e a diretoria tem uma visão consolidada do negócio.

Como trabalhos futuros, destacam-se a publicação dos recursos na Azure, a autenticação de
usuários com perfis de acesso por time, o registro do histórico de alterações de cada apólice
(endosso), testes automatizados no \emph{frontend} e, com o crescimento do volume de dados, o
uso de indicadores pré-calculados para acelerar a \emph{dashboard}.
